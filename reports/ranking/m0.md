## Available evaluation information

Both profile splits contain `text`, `hidden_slots`, `target`, `target_profile`, `related`, `related_in_pool`, `resolutions`, `latent_reveal`, and contradiction/plant fields. Exact targets and relation categories support M2 evaluation: target = 4, Primary-Short = 3, Primary-Long = 2, Supplemental = 1. Labels stay on the evaluator side of the interface.

Neither split includes ordered conversation turns, per-sentence evidence statuses, or pre/post tracker snapshots. The resolution/reveal fields can support a future simulator but do not constitute recorded conversation history. M6–M8 require upstream replay snapshots or independently reviewed fixtures with stable evidence IDs, statuses, stance/reason labels, and fixed tracker state. This does not block M1.

## Typed runtime contract

Implemented in `recommender/schemas.py`:

- `RankingRequest`: all six finite scores in `[-1,1]`, allowed `observed_types`, accumulated user-only utterances, and positive `top_k` (default 100).
- `RankedOccupation`: code, title, final rank, supplied occupation z-vector, optional fused score, per-signal scores/ranks, and task evidence.
- `RankingResponse`: an explicit `ranked` or `no_signal` envelope for the policy. The later minimum `rank(...) -> list[RankedOccupation]` can expose `response.occupations`; the policy adapter should retain status/reason.
- `OracleInput`: separate offline z-scale adapter. It preserves `hidden_slots` without clamping and copies only vector/text inputs, never target or relevance labels. Reports using this adapter must say `oracle`.

Mock runtime request:

```python
RankingRequest(
    interests={"R": 0.0, "I": 0.55, "A": 0.0, "S": 1.0, "E": 0.0, "C": -0.55},
    observed_types={"I", "S", "C"},
    user_sentences=["I enjoy helping people and investigating problems.", "I dislike repetitive paperwork."],
    top_k=100,
)
```

Unknown `R=0` is distinguished from observed neutral `R=0` by membership in `observed_types`. Upstream confidence merging belongs to the tracker; the ranker must not apply confidence again implicitly. The caller is responsible for excluding bot questions because raw strings do not encode speaker roles.

Mock no-signal result (illustrative, not computed by an M0 ranker):

```python
RankingResponse(
    status="no_signal",
    occupations=[],
    reason="No observed nonzero interests and no usable text signal.",
)
```

A successful future response has `status="ranked"` and a nonempty list of `RankedOccupation` records. M0 does not fabricate occupation scores. The policy must accept fewer than 100 results and an explicit empty result. A zero-only vector with no usable retrieval returns `no_signal`; a zero-only vector with usable text may rank through retrieval in later milestones. `has_text` reports nonblank input, not proof of retrieval relevance; each future ranker must decide whether its signal is usable.

Running the audit against the real data also passes.

Ranking quality and per-turn ranking latency are not applicable yet. The saved audit duration measures validation only. Source data remains ignored by the existing repository rule; teammates need the same six local datasets, checked against the saved fingerprints, to reproduce the audit.
