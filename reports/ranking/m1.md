The loader verifies required columns, code uniqueness, titles, finite supplied z-scores, complete vectors, and valid job zones. Fully missing z-vectors are excluded; partial vectors and malformed numeric values fail clearly. Only Job Zones 4–5 with complete supplied vectors are eligible. The runtime loader derives pool size from data; **378 is verified in the real-data acceptance test, not hard-coded into ranking logic**. Codes stay strings and z-scores are never standardized again.

For each occupation, the score is:

```text
sum(interests[t] * occupation_z[t] for observed t in R,I,A,S,E,C order)
```

Scores sort descending; exact ties sort by occupation code ascending. Fixed dimension order ensures scoring does not depend on set iteration order. Scores may be negative and are retained. Final and structured signal ranks are one-based. Return at most `top_k` results (default 100); oversized requests return the available pool. Fusion scores remain `None` and task evidence remains empty because those features are outside M1.

## Runtime interface and no-signal behavior

```python
from recommender.structured import StructuredRanker

ranker = StructuredRanker()  # load once; default data/occupations.csv
response = ranker.rank(
    interests={"R": 0.0, "I": 0.55, "A": 0.0, "S": 1.0, "E": 0.0, "C": -0.55},
    observed_types={"I", "S", "C"},
    user_sentences=[],
    top_k=100,
)
```

The existing `RankingRequest` validates all six finite runtime interest values in `[-1,1]`, allowed observed keys, string-list history, and a positive integer `top_k` (booleans rejected). The public method preserves M0's `RankingResponse` wrapper: `response.status`, `response.reason`, and `response.occupations`.

No observed dimensions, or only observed zero-valued dimensions, returns `status="no_signal"`, an empty occupation list, and an explicit reason. Nonzero values in unobserved dimensions cannot create a signal. Known zero and unknown dimensions remain distinguishable through `observed_types`, although their numerical contribution is zero. Text alone cannot produce rankings at M1.

`user_sentences` is accepted and validated for compatibility, then ignored by structured scoring. It is not used to infer interests. No text-dependent acceptance tests, user-history assembly, sentence splitting, lexical normalization, or evidence filters were introduced.

## Future integration contracts and unresolved assumptions

- The caller will supply chronological user-only history through the latest turn, preserving wording, negation, and repeated messages. A list item is a user message, potentially containing multiple sentences. Caller ownership, message representation, and policy invocation remain pending teammate agreement; these do not block this structured-only local implementation.
- User/bot filtering and conversation storage belong to orchestration. Hybrid preprocessing remains a future contract: BM25-specific lexical preparation must not modify MiniLM's natural-language input. No preprocessing module was created at M1.
- The policy must agree on the existing status envelope and accept fewer than 100 results. M0's local response decision was retained; no external integration agreement is claimed.
- Tracker confidence merging remains upstream. M1 applies no second confidence weighting. Oracle z-scale inputs remain separate from runtime inputs; the existing M0 oracle adapter was not expanded or used here.
- Accuracy evaluation was subsequently implemented at M2; see its linked decision report. BM25, MiniLM, FAISS, RRF, task evidence selection, and lifecycle/familiarity experiments remain later milestones.

## KIV: scoring alternatives requested for later evaluation

- The user requested revisiting the simple linear structured score as a possible improvement. Retain M1 as the reproducible control; this is a research idea, not an accepted replacement or evidence of a defect.
- Implement the planned BM25 occupation-text retrieval (M3), MiniLM task retrieval (M4), and occupation-level RRF before deciding whether structured scoring needs replacement. BM25 supplies a separate lexical signal; it does not directly replace numerical RIASEC matching.
- The M2 evaluator now exists. After the required retrieval baseline also exists, compare justified alternatives, potentially including nonlinear structured scoring, on development data with fixed inputs and candidate pool. Record gains, regressions, and complexity before adoption; do not tune on held-out profiles.
- Multi-turn integration must consume the tracker's current cumulative per-user profile and user-only history. Recompute occupation rankings from each updated snapshot; do not sum occupation scores across turns or re-merge already accumulated tracker values in the ranker. Tracker merging and contradiction resolution remain upstream responsibilities.
